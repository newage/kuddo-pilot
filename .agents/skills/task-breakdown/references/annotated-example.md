# Розібраний приклад

Реальний `tasks.md`, написаний розробником, з поміткою, який прийом де спрацював. Проєкт на TypeScript/Hono, але прийоми від стека не залежать.

Зміна: додати ендпоінт зрізу прогресу вивчення. 47 рядків, 4 розділи, 21 пункт.

Одне застереження: блоків `## Межі зміни` і `## Виправдана складність` у корпусі немає — їх у скіл додано пізніше, з практики change budget і з гейтів spec-kit. Розробник тримав межі розсипом по пунктах, і це працювало, але перевірити такий розсип механічно неможливо. Нижче показано, як ті самі межі виглядали б зібраними в блок.

---

## Чого в корпусі бракувало — межі зміни

Розсипані по пунктах межі цієї зміни, зібрані докупи:

```markdown
## Межі зміни

Змінюємо: backend/src/features/user-progress/**, word.service.ts,
           scripts/fixtures/cleanup-orphan-word-progress.ts, src/index.ts
Не чіпаємо: word-set.service.ts (крім читання), word-progress/** (цикл імпортів)
Нові залежності: немає
Публічні контракти: новий ендпоінт, наявні без змін
```

Чотири рядки, які звіряються з `git diff --name-only` за секунду. У самому корпусі цю саму інформацію доводиться збирати з пунктів 1.3, 3.2 і преамбули розділу 3.

## Розділ 1 — передумова, а не основна робота

```
## 1. Прибирання прогресу при видаленні набору

Передує ендпоінту: доки рядки прогресу переживають видалення набору,
`user_learned_words` завищений на слова наборів, яких уже немає.
```

← **Преамбула розділу.** Два рядки, і зрозуміло, чому баг-фікс стоїть перед основною фічею. Без цього перший порив — почати з ендпоінта, бо задача ж «про ендпоінт».

```
- [ ] 1.1 Тест у `word.service.test.ts` (файл новий): слова власника
      видаляються → `removeProgressForWords` викликано саме з тими id,
      які реально видалились.
```

← **Тест передує реалізації** і містить **точну координату** — включно з поміткою, що файл новий.

```
- [ ] 1.3 У `deleteWordsByIdsForUser` (`word.service.ts:620`) зібрати id
      фактично видалених слів і одним викликом
      `wordProgressService.removeProgressForWords` прибрати їхній прогрес.
      Саме тут, а не в `wordSetService.deleteById` (`word-set.service.ts:660`):
      там доступний лише повний `wordSet.words`, по ньому знісся б і чужий
      прогрес.
```

← Найщільніший пункт корпусу. **Координата з рядком**, **межа з обґрунтуванням** і — головне — обґрунтування через **наслідок** («знісся б чужий прогрес»), а не через смак («тут доречніше»). Виконавець, який не знає цієї деталі, обрав би саме друге місце: воно виглядає чистішим.

```
- [ ] 1.4 Перевірити, що пакетне видалення слів (`word.service.ts:222`)
      не задвоює прибирання — воно кличе `removeProgressForWords` самостійно.
```

← **Перевірочний пункт.** Нічого не змінює. Коштує рядок, економить розбір «чому цифра поїхала вдвічі».

## Розділ 3 — основна робота

```
## 3. Ендпоінт зрізу прогресу

Нова фіча `backend/src/features/user-progress/` — без ентиті, за зразком
`training`. Агрегатор не класти в `word-progress`: той імпортує лише сховище,
а `word-set.service.ts` уже імпортує його — вийшов би цикл.
```

← Преамбула несе одразу **зразок** («за зразком `training`»), **заборону** («без ентиті») і **межу з обґрунтуванням** («вийшов би цикл»). Три прийоми в двох реченнях — саме тут задається обсяг усього розділу.

```
- [ ] 3.2 `user-progress.mapper.ts` (не `utils`: це проєкція сутностей у
      вигляд клієнта, а мапер — те місце, де за AGENTS.md живуть похідні поля)
```

← **Межа**, обґрунтована правилом проєкту. Дешевий випадок: рішення вже записане в документації, задача просто на нього посилається.

```
- [ ] 3.4 ... Нових запитів до сховищ не заводити.
```

← **Заборона** в кінці пункту, рівно там, де виникає спокуса: пункт описує підрахунок, і найпростіший шлях — додати ще один запит.

```
- [ ] 3.7 Змонтувати в `src/index.ts` на `/dictionary-api` — не на фіксований
      префікс, інакше параметри шляху не резолвляться. Перевірити, що роут
      не конфліктує з `/{src}/{dst}/user-sets`.
```

← **Межа** плюс **перевірочний пункт** в одному рядку. «Інакше параметри шляху не резолвляться» — це знання, здобуте болем; без нього виконавець зробить логічну, але неробочу річ.

## Розділ 4 — закриття

```
- [ ] 4.1 Після `openspec archive` замінити Purpose у
      `openspec/specs/user-progress-overview/spec.md` — `archive` підставляє
      заглушку `TBD - created by archiving change…`, яка проходить `--strict`
      і мовчки лишається назавжди.
```

← Пункт про **інструментальну пастку**: валідація не ловить, тож пастка лишається назавжди. Такі пункти неможливо вивести зі специфікації — вони беруться з досвіду й тому мусять бути записані.

```
- [ ] 4.3 ОСТАННІМ: прогнати `./docker/scripts/check_spec_sync.sh` і по
      кожному пункту вирішити, чи потрібна правка специфікації.
```

← Обов'язковий пункт з правил проєкту. Слово «ОСТАННІМ» стоїть не для краси: звіт має сенс тільки після того, як код уже змінений.

## Що з цього переносне

| Прийом | Скільки коштує | Що ловить |
|---|---|---|
| Преамбула розділу | 1–2 рядки | переставлений порядок робіт |
| Точна координата | частина рядка | «архітектурно чисте», але не те місце |
| «За зразком X» | посилання | винайдений з нуля патерн |
| Межа з наслідком | 1 рядок | цикли, не та область даних, зламані сусіди |
| Заборона в пункті | 1 рядок | рефакторинг заодно, зайве узагальнення |
| Перевірочний пункт | 1 рядок | мовчазні поломки суміжного |

Жоден із них не займає більше рядка. Уся різниця між 35-рядковою задачею, що тримає межі, і 35-рядковою, що не тримає, — це шість рядків такого типу.

## Контрприклад

Той самий підхід, доведений до крайності, дає протилежну проблему. План, згенерований публічним скілом на додавання **однієї nullable-колонки**, — 377 рядків з повним інлайновим кодом кожного кроку, командами запуску і наративом про те, як рішення змінювалось по ходу.

Інлайновий код у задачі шкодить двічі: він застаріває швидше за сам код і перетворює план на гірший дублікат реалізації. Задача називає **місце й межу**; як саме писати — робота виконавця.

Орієнтир з корпусу: 27–47 рядків на зміну.
