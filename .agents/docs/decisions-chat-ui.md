# Журнал рішень: власний чат-UI для дитини (Kuddo Pilot)

## Проблема
Дитині потрібен простий чат з AI-вчителями: вхід через Google, збережена історія розмов, вибір вчителя (предмета). Open WebUI надлишковий: чужий UI, власні ролі та історія, яку доводиться вимикати, окремий довгоживучий хостинг. Без цього асистента не можна безпечно дати дитині. Історія чату не росте безмежно: у БД лишаються ≤10 останніх записів, один із яких — короткий підсумок усіх попередніх, щоб не зберігати все й щоб AI не губив контекст. Роль `parent` і статистика відкладені.

## Дано
- Чат-UI пишемо самі, Open WebUI і OpenAI-сумісний шлюз не потрібні — перевірено: рішення користувача.
- Стек з `prepare.md` §3 лишається: Next.js (App Router), Postgres, Auth.js + Google OAuth, `@google/genai`.
- Мета підсумовування: не тримати в БД усі повідомлення чату і зберегти контекст для AI (10 останніх записів, один з яких — підсумок попередніх) — слова користувача.
- Правило підсумовування чату з `prepare.md` §6 лишається без змін (≤10 записів, кумулятивний підсумок, атомарно).
- Поза межами цього етапу: `parent`, статистика, зв'язок parent↔діти.
- Ролі на цьому етапі: `admin`, `user`.
- Локальна розробка — обов'язково через Docker; Docker-файли в окремій папці в корені репозиторію — рішення користувача.

## Концепт рішення
**Обрано:** один застосунок Next.js: UI, API-роути, Auth.js і виклики Gemini.
**Чий:** запропонував розробник
**Чому:** усе вже в стеку, один деплой на Vercel, без окремого бекенду і без хостингу Open WebUI.
**Відкинуто:**
- Залишити Open WebUI + шлюз — власний UI/історія/ролі дублюють наші, потрібен окремий хостинг.
- Окремий SPA (Vite/Svelte) + бекенд — другий сервіс без виграшу.

**UI:** Vercel AI SDK (`useChat`, стрімінг) + shadcn/ui.

## Вектор
```
Дитина ─► Next.js UI (useChat) ─► POST /api/chat ─► перевірка сесії + права на вчителя
                                        │                  │
                                        │                  ▼
                                        │             Postgres (чат: ≤10 записів)
                                        ▼
                                   Gemini (стрімінг) ─► відповідь у UI
                                        │
                                        └─ після відповіді (фон): якщо записів = 10 → згортання в підсумок (транзакція, блокування чату)
```
- Один маршрут `/api/chat`: Auth.js-сесія, перевірка доступу ролі до вчителя, контекст = підсумок + поточні записи.
- Підсумовування — у фоні після відповіді, з блокуванням чату в транзакції.
- Admin-портал мінімальний: користувачі, ролі, реєстр вчителів і їхніх промптів, доступи.

## Деталі
### Коли згортати історію
**Рішення:** після відповіді, у фоні (напр. `after()` на Vercel); відповідь без затримки.
**Чому:** дитина не чекає другого виклику Gemini; гонку закриває блокування чату в транзакції.
**Альтернатива:** перед відповіддю (затримка на кожному 10-му записі); ліниво перед наступним запитом (промпт тимчасово довший).

### Що таке «встановлені моделі» (рішення 1, переглянуто)
**Рішення:** модель Gemini одна (id у конфігурації). Дитина вибирає не модель, а «вчителя»: запис у БД з назвою, предметом і системним промптом (математика, фізика тощо). Усі «вчителі» йдуть у Gemini з різними системними промптами.
**Чому:** для дитини це чат із вчителем предмета, а різниця між «вчителями» лише в промпті, тож окремі моделі і провайдери не потрібні.
**Наслідки:**
- Сутність `AI-модель` з `prepare.md` замінюється на `teacher` (назва, предмет, системний промпт, активність).
- Доступ ролей прив'язується до `teacher`, а не до моделі Gemini.
- Системний промпт підставляється на кожен запит і в чат-записи/підсумок не потрапляє.
- Чат прив'язаний до `teacher` при створенні, зміна вчителя = новий чат.
- Admin-портал керує списком вчителів і їхніми промптами.
- Промпт підсумовування один і той самий для всіх вчителів і не залежить від предмета.
**Альтернатива (відкинуто раніше):** кілька моделей/провайдерів у реєстрі (B), автовиявлення з Ollama (C). Не потрібні, бо модель одна.

### Що бачить дитина після згортання
**Рішення:** підсумок показується як перше повідомлення чату, далі нові повідомлення.
**Чому:** відповідає інваріанту §6 і чесно показує, що відомо моделі, без зайвого сховища.
**Альтернатива:** прихований підсумок (чат виглядає обрізаним); окрема повна історія для UI (суперечить §6, GDPR).

### Збій фонового згортання
**Рішення:** записи лишаються, наступне повідомлення знову пробує згорнути (чат тимчасово довший за 10).
**Чому:** без втрати даних, інваріант відновлюється на наступній спробі, транзакція не лишає половинчастого стану.
**Альтернатива:** видалити найстаріше без підсумку (втрата контексту); блокувати чат (дитина застрягає через збій сервісу).

### Скільки чатів у дитини
**Рішення:** багато чатів на пару «користувач + вчитель»; «Новий чат» з вибором вчителя, окремий підсумок і ліміт ≤10 записів на кожен чат.
**Чому:** теми не змішуються в одному підсумку, звичний UX списку історії.
**Альтернатива:** один чат на модель (змішування тем); авто-назва від Gemini (зайвий виклик на кожен новий чат).

Наслідок для `prepare.md` §6: «чат» тепер окрема сутність (id), а не пара користувач+модель; правило підсумовування діє per-чат.

### Видалення чату
**Рішення:** дитина може «видалити» чат, фактично він ховається (soft delete); записи в БД лишаються.
**Чому:** вимога користувача; дані не втрачаються, UI чистий.
**Відновлення:** зміною статусу в БД (UI для відновлення не потрібен на цьому етапі).
**Наслідок:** прихований чат не показується в списку; правило ≤10 записів діє й для нього.

### Профіль дитини
**Рішення:** дитина має профіль: ім'я, вік, хобі та вільне текстове поле «розкажи про себе». Зберігається в БД, редагується дитиною в будь-який час.
**Чому:** вимога користувача; персоналізує відповіді вчителя.
**Наслідок:** профіль додається до контексту запиту разом із системним промптом вчителя (див. припущення).

### Локальна розробка
**Рішення:** локальне середовище працює лише через Docker (застосунок Next.js, Postgres). Усі Docker-файли (compose, Dockerfile) лежать в окремій папці в корені репозиторію (напр. `docker/`), а не розкидані по корені.
**Чому:** вимога користувача; однакове середовище в усіх, без локальної установки Node/Postgres, корінь проєкту чистий.
**Наслідок:** запуск без Docker не підтримується і в документації не описується; Vercel лишається лише для деплою.

### ORM і міграції
**Рішення:** Drizzle ORM з SQL-міграціями (`drizzle-kit`).
**Чому:** легкий, типобезпечний, добре працює з Neon/Vercel Postgres у serverless.
**Альтернатива:** Prisma (важчий клієнт), Kysely (більше ручної роботи зі схемою).

### Перший admin і вчителі
**Рішення:** email першого admin береться зі змінної `ADMIN_EMAIL`: користувач з цим email отримує роль `admin` при першому вході. Вчителів і доступи далі створює admin у порталі; початкових даних у міграціях немає.
**Чому:** без seed-даних у коді, відтворювано в Docker і на Vercel.
**Альтернатива:** seed у міграції (дані в коді); ручний запис у БД (не відтворюється).

## Припущення
- Нові користувачі не мають доступу, доки admin не призначить роль (з `prepare.md` §5) — не блокує.
- Назва чату береться з першого повідомлення (обрізана), без виклику Gemini — не блокує.
- Редагування системного промпту вчителя діє і на вже наявні чати (береться актуальний промпт, версіонування немає) — не блокує.
- Для `parent` і статистики схему БД не проєктуємо зараз, але `user_id` і `chat_id` у чатах лишають шлях до цього — не блокує.
- GDPR і ретеншн не потрібні: персональні дані — лише ім'я, вік і самоопис дитини (рішення користувача).
- Профіль дитини підставляється в контекст кожного запиту разом із системним промптом вчителя, у чат-записи й підсумок не потрапляє — не блокує.
- Самоопис — довільний текст; фільтрації вмісту на цьому етапі немає — не блокує.
