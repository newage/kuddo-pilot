# Design

## Context

Next.js App Router, Auth.js; увесь UI — захардкоджені українські рядки (див. `login`, `waiting`, `profile`, `ChatList`, `ChatView`, `/api/chat`). Перший екран — `/login` (`authorized` у `auth.config.ts` пускає без сесії). Мотивація — proposal.md.

## Goals / Non-Goals

**Goals:** два словники `uk`/`pl`; вибір мови до входу; відповідь вчителя обраною мовою; без нових залежностей і змін БД.

**Non-Goals:** URL-префікси мови, переклад збереженого вмісту, більше двох мов.

## Decisions

1. **Cookie `locale` без URL-маршрутизації; без cookie — `Accept-Language`.** Читається на сервері через `cookies()`; якщо її немає або значення невалідне, `getLocale()` читає `headers().get("accept-language")` і передає `negotiateLocale()` (розбір q-значень; перший підтримуваний тег за пріоритетом: `pl*` → `pl`, `uk*` → `uk`, інакше `uk`). Cookie при автовизначенні не ставиться — вона лише фіксує явний вибір користувача. Працює на `/login` до автентифікації, переживає OAuth-редірект, не потребує змін middleware/matcher. *Альтернативи:* `next-intl` з `/[locale]/…` — перебудова всіх маршрутів і редіректів Auth.js, надлишково для двох мов; зберігати в БД — не працює до входу.
2. **Власний мінімальний i18n у `src/i18n/`:** `locales.ts` (`LOCALES`, `DEFAULT_LOCALE`, `parseLocale`), `messages/uk.ts`, `messages/pl.ts` (тип `Messages` виводиться з `uk`, `pl` мусить йому відповідати — пропуск ключа ловить `tsc`), `server.ts` (`getLocale()`, `getMessages()`). Клієнтські компоненти (`ChatView`) отримують потрібні рядки пропсами від серверної сторінки, без контексту.
3. **Перемикач — server action `setLocale(locale)`:** валідує через `parseLocale`, ставить cookie (`path=/`, 1 рік, `sameSite=lax`) і `revalidatePath("/", "layout")`. Компонент `LanguageSwitcher` — форма з двома кнопками `UK | PL` (працює без JS), поточна мова позначена `aria-current`. Розміщення: `/login` (по центру над кнопкою), `ChatList` (низ панелі), `/waiting`.
4. **`<html lang>`** береться з `getLocale()` у кореневому layout (це робить усі сторінки динамічними, що для застосунку з автентифікацією прийнятно).
5. **Мова відповіді вчителя:** `ChatView` передає `locale` у тілі `/api/chat`; роут через `parseLocale` (невалідне → `uk`) додає в кінець системної інструкції рядок «Відповідай польською/українською мовою» (у `buildContext` новим параметром `locale`). Підсумок пишеться мовою повідомлень чату, а не мовою інтерфейсу: у `SUMMARY_SYSTEM_PROMPT` рядок «Пиши українською» замінюється на явну вимогу писати тією ж мовою, що й записи розмови (для змішаних — мовою останніх повідомлень дитини); `locale` у підсумовування не передається. *Альтернатива:* брати cookie в роуті — але явне поле в тілі тестується простіше й не залежить від cookie-політик.
6. **Помилки `/api/chat`:** тексти через `getMessages()` за cookie запиту (у роуті локаль береться з тіла, а для помилок до розбору тіла — з cookie через `getLocale()`).
7. **Admin локалізується тим самим механізмом:** окремий розділ `admin` у словниках; admin-сторінки й `LanguageSwitcher` у `admin/layout.tsx`. Server actions (`users-actions`, `access-actions`, `teachers/actions`) кидають помилки текстами зі словника через `getMessages()`. Дані (назви/промпти вчителів, email) не перекладаються.
8. **Промпти вчителів англійською:** вони лежать у БД і не змінюються; тому інструкція мови (п. 5) обов'язкова й іде останньою, щоб англомовний промпт не змушував відповідати англійською. Англомовність самих промптів — справа admin-контенту, у коді правок не потребує.

## Risks / Trade-offs

- [Польські переклади якістю] → короткі UI-рядки; ревізія носієм мови до релізу, словник — єдине місце правок.
- [Дрейф ключів між словниками] → тип із `uk` змушує `pl` бути повним.
- [`cookies()` у layout робить усе динамічним] → усі сторінки й так за автентифікацією.
- [Системна інструкція мови може конфліктувати з промптом вчителя] → інструкція додається останньою; перевірити вручну на обох мовах.
